# Independent-user trial — not yet run

Start the 14-day clock only after cloud acceptance and the fresh-host restore drill pass. Give one peer their own project-scoped token. Do not claim lab adoption or saved time from developer-only tests.

The peer must prepare, transfer, locate and fetch at least three completed datasets. Include a small bundle, the complete CATS bundle and a representative larger bundle. Ask the peer to interrupt one transfer and resume it using the documented CLI. Observe without taking over; record every intervention.

For each task record: date, dataset class/bytes/file count, command, result, time, assistance required, error code, expected versus observed behavior, and feedback. Do not collect tokens or unnecessary researcher data. Record daily uptime/dependency incidents, disk and S3 growth, backlog, backup success and actual cost.

Before completion, implement at least one concrete improvement driven by observed peer difficulty and repeat the affected task. Link the before/after evidence to the change. Obtain permission before quoting identifiable feedback publicly.

Release gates still requiring a real operator/peer:

- AWS multipart, version pinning, crash and network-loss acceptance.
- SSH access and tokens across separate machines.
- Fresh deployment, image upgrade/rollback and alert-delivery checks.
- Fresh-host restore within the measured target and verified backup RPO.
- Fourteen days of operating records, three peer datasets and a feedback-driven change.
- Final workload benchmarks under controlled cloud/network conditions, with all failed runs retained.

Until these pass, describe the project as a locally validated release candidate with recovery tests—not a demonstrated lab deployment.
